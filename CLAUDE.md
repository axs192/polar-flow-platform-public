## What this is

Consolidating a working-but-fragmented Polar Flow webhook pipeline (currently 4 separate local folders + hand-built AWS infra, no IaC, no CI/CD) into this one repo: Terraform, CI/CD, application code, docs.

## Hard constraints — do not violate

- **Never modify the old/current production AWS account** (referred to as `<OLD_ACCOUNT_ID>` in docs — it's redacted deliberately, see below). This migration builds a fresh stack in a *new* AWS account (`polar-app-prod`, local CLI profile of the same name) and only cuts real traffic over once validated end-to-end. The old account is read-only reference material until the explicit, separate decommission step.
- **Never commit real AWS account IDs, the Organization ID, or the live API Gateway ID** to this repo (git or otherwise) — the API Gateway ID alone reveals the exact live production webhook URL. Use the `<OLD_ACCOUNT_ID>` / `<ORG_ID>` / `<API_GATEWAY_ID>` placeholder convention already in `docs/architecture.md`. Real values live in `~/.aws/config` (local, gitignored by definition) or later in gitignored `terraform.tfvars`/CI secrets — never in markdown or code.
- **Python tooling is `uv` only** — no `pip install`, `pipx`, or Poetry. If a tool is needed (e.g. `pre-commit`), it's `uv tool install <name>`.

## Known gotchas

- **`.pre-commit-config.yaml` pins gitleaks to `v8.18.4`, not latest.** Gitleaks ≥v8.19 uses the `wasilibs/go-re2` WASM regex engine, which silently detected *zero* secrets in this sandboxed dev environment (no error — verified against AWS-key and PEM-private-key test fixtures). v8.18.4 uses Go's stdlib regexp and was confirmed working end-to-end (including blocking a real `git commit`). Re-verify with the same kind of fixture test before ever bumping this pin.
- The `gitleaks-system` pre-commit hook ID upstream is missing `pass_filenames: false` (unlike its siblings) — we override it in `.pre-commit-config.yaml`. Don't remove that override.
- A fresh clone needs `uv tool install pre-commit && pre-commit install` once — `.git/hooks/` isn't version-controlled, only `.pre-commit-config.yaml` is. Documented in the README too.
- **Always run each service's tests as `python -m unittest discover -s tests -t .` (note `-t .`), never bare `-s tests`.** Without `-t .`, unittest treats `tests/` itself as the top-level dir, so `tests/__init__.py` never actually executes — including its `os.environ[...]` dummy-AWS-credentials setup that every service's `tests/__init__.py` relies on to keep moto-based tests hermetic. This masked itself for months of local dev in this sandbox because `~/.aws/config` has a real default region, which boto3 silently fell back to — a machine with zero AWS config (a fresh clone, or a clean CI runner) hits `botocore.exceptions.NoRegionError` instead. Caught this exact way on the first real GitHub Actions run. `.github/workflows/test.yml` already uses `-t .`; if you ever add a new way to invoke the suite (a Makefile target, a different CI job), carry it over.
- **Inside a zip-based Lambda's own source, never write `from src.app...` / `import src...`.** `terraform/modules/lambda_function`'s `source_dir` points at a service's `src/` directory, and Terraform's `archive_file` zips that directory's *contents*, not the directory itself — so the deployed zip's root is `app/…`, there is no `src/` inside it. `-t .` (the gotcha above) makes `src` a real importable package during local test runs, which is exactly why this class of bug survives every test suite and only surfaces live: it bit this repo twice in the same incident — once in Terraform's `handler` attribute (`app.lambda_handler.lambda_handler`, not `src.app...`), once independently inside the handler file's own imports (fixed with a *relative* import, `from .config_loader import config_loader`, which resolves correctly under both the local `src.app` package name and the deployed zip's bare `app` name — an absolute `from app.config_loader import ...` would have re-broken the local tests instead). Confirmed live via CloudWatch (`Runtime.ImportModuleError`) on all 3 zip-based services before both fixes landed. If you add a 4th zip-based Lambda or touch this pattern, verify the fix against a real simulated copy of the zip layout, not just the local test suite — the local layout can't catch this bug by construction.
- **In docs, `<angle-brackets>` mean "substitute this" — a bare word (`ID`, `SECRET`, `TOKEN`) reads as a plausible literal value and gets copy-pasted verbatim.** Bit a real onboarding walkthrough twice in the same session (once for `--client-id`/`--client-secret`, once for `--access-token`/`--member-id`) before the convention was applied consistently. But `<foo>` is *also* unsafe inside a live, non-comment shell command line specifically — it's bash input-redirection syntax, so a literal copy-paste there fails with a confusing shell error instead of the intended "go fill this in" cue (verified by running every shell code block in a doc through `bash -n` after an edit, which is now worth doing after touching any runbook/README with copy-pasteable commands). Reserve `<angle-brackets>` for comments/prose/example-output lines; for a value a reader must type into a runnable command, prefer capturing it into a shell variable first (`read -r VAR` or `VAR=$(...)`) or an env-var/`.env` fallback, then reference `"$VAR"`.
- **A `terraform destroy` (including a deliberate rehearsal — see `docs/runbooks/teardown-rehearsal.md`) wipes the *entire* Secrets Manager secret, not just whichever keys you're focused on repopulating.** `terraform/environments/prod/secrets.tf` deliberately never manages the secret's contents, only the empty container, so every manually-populated key is gone after a destroy — Polar's (`client_id`/`client_secret`/`access_token`/`user_id`/`POLAR_WEBHOOK`) *and* Meta/OpenAI's (`META_AUTH`/`META_NOT_SEC`/`META_VERIFY_TOKEN`/`OPEN_AI_AUTH`) alike. Confirmed via CloudTrail after a real rehearsal: the secret's ARN gets a new random suffix on recreate, which Secrets Manager assigns once, permanently, at creation — a different suffix is conclusive proof of a destroy+recreate, not an in-place update. Re-populating only the half you're actively working on (easy to do, since nothing errors at rebuild time) leaves other services silently running against missing config.

## Development practices

- **Python tooling is `uv` only** (see Hard constraints above): `pyproject.toml` + `uv.lock` per service, `[dependency-groups] dev` for test deps, `uv sync`/`uv run`. Never `pip install` directly.
- **`ruff` (lint + format) and `bandit` (security lint) are configured once at the repo root** (`pyproject.toml`) and must stay clean across the whole `services/` tree. Findings get fixed at the root cause — rename the flagged identifier, delete the dead code, add the missing timeout, whatever it takes. Never suppress with `# nosec`/`# noqa` as a shortcut.
- **Every service's test suite runs fully offline** — `moto` for AWS, `responses` for `requests`-based HTTP, `respx` for `httpx`-based HTTP (e.g. the OpenAI SDK). Prefer registering fixtures against real status codes (200/400/401/404/409/500) over mocking a whole class away — the goal is to exercise real exception paths (`raise_for_status()`, real SDK error types), not just assert "a mock was called." This has repeatedly surfaced real bugs that pure mocking would have hidden.
- **Coverage is gated in CI per service** (`[tool.coverage.report] fail_under` in each service's `pyproject.toml`, enforced by `.github/workflows/test.yml`), calibrated to each service's real current number plus a small buffer — not an aspirational target that fails on day one. When coverage is low, prioritize by risk (Lambda entrypoints and auth/token logic first, thin declarative wrapper classes last), not by raw line count.
- **Three-hat review (security / testing / developer) at major milestones** — before a repo-visibility decision, and before starting a new major roadmap phase — not just once at the end. Findings and resolutions get written into `docs/architecture.md`'s "Three-Hat Reviews" section so status survives a fresh session, not just chat history. Re-verify directly (grep, re-run the actual CI command, re-scan history) rather than reciting a prior review from memory.

## Git workflow — branch + PR, not direct pushes to `main`

Adopted once CI was confirmed green end-to-end on `main` (first real GitHub Actions run — see `docs/architecture.md`'s Three-Hat Reviews / roadmap for that history).

- **Every change goes through a feature branch + PR**, even for a single-person repo: branch off latest `main`, commit there, `gh pr create`, wait for `Test` and `Security scan` to go green on the PR, then merge. Delete the branch after merging.
- **This is convention, not a GitHub-enforced rule.** Branch protection on `main` (require PR before merge, require status checks) needs GitHub Pro for a private repo — checked directly (`gh api ... branches/main/protection` returned 403: "Upgrade to GitHub Pro or make this repository public to enable this feature"). Decided to stay on Free and private rather than pay for enforcement or reverse the private-repo call from the earlier three-hat review. That means nothing on GitHub actually stops a direct push to `main` — the discipline is the enforcement. Don't push straight to `main` going forward; open a PR even for something that feels trivial.
- If this repo ever moves to GitHub Pro (or public), revisit turning the convention above into real branch protection — but **check path-filtering first**. Both `test.yml` and `security-scan.yml` now gate their per-service matrices and several single jobs on a `changes` job (`dorny/paths-filter`), so a PR touching only one service legitimately produces fewer than the full 7+11 checks. A job *skipped* by a path filter but listed as a GitHub-required status check leaves PRs stuck "pending" forever — a well-known GitHub Actions footgun, not a live problem today only because Free-tier branch protection isn't enabled. Any required-checks list adopted later needs to account for this (e.g. a single always-run "CI passed" gate job that `needs:` everything, rather than requiring each matrix leg by name).
- Same GitHub Advanced Security gate also blocks SARIF upload to the Security tab from the gitleaks job — already worked around in `security-scan.yml` (the scan itself still gates the build on its own exit code, just without the Security-tab UI).
- **No auto-merge, ever — a PR only merges after explicit human review and approval.** Since branch protection can't enforce this (see above), it's a hard rule for Claude specifically: open the PR, let CI run, then stop and wait for the user to review and merge it themselves. Don't run `gh pr merge` unprompted, even if every check is green.
- **Commit in small, discrete chunks and push regularly — don't batch a whole feature into one commit pushed at the end.** Each logical step (one file, one fix, one small addition) gets its own commit, pushed to the PR's branch as you go, not accumulated locally. This gets CI running against real intermediate states, so a break surfaces against the specific small change that caused it, not buried in a large diff at the end.

## AWS access

- Default CLI profile → the **old** account (discovery/reference only).
- `--profile polar-app-prod` → the **new** account, via `OrganizationAccountAccessRole` (configured in `~/.aws/config`, not in this repo).
- **Console access (switch role)**: Account: `<NEW_ACCOUNT_ID>`, Role: `OrganizationAccountAccessRole` — the standard auto-created cross-account role on every Organizations member account, reachable from a management-account console login via **Switch Role**. Organization ID: `<ORG_ID>`, management account: `<OLD_ACCOUNT_ID>`. Real values live in `~/.aws/config` / your own notes, never here.
- **`services/polar-onboarding` does not inherit this convention automatically.** Its own AWS calls (`webhook create --store-secret-name`, via `secrets.py`) fall back to plain boto3 default-credential resolution unless `--aws-profile polar-app-prod` (or the `AWS_PROFILE` env var / `.env` entry) is passed explicitly — omitting it silently targets whatever the ambient default profile is (the **old** account, per the bullet above), not `polar-app-prod`.
